POST /auth/cadastro

{ "name": "Amélia Macedo", "email": "amelia@exemplo.com", "password": "senhaSegura123" }
→ 201 { "id": "uuid", "name": "Amélia Macedo", "email": "amelia@exemplo.com" }

Nome de 2 a 120 caracteres; e-mail válido, único e gravado em minúsculas; senha de 8 a 72 caracteres, guardada com hash bcrypt. E-mail já existente → 409.

POST /auth/login

{ "email": "amelia@exemplo.com", "password": "senhaSegura123" }
→ 200 { "accessToken": "<JWT>" }

Credenciais erradas → 401 com a mesma mensagem para e-mail inexistente e senha errada. O JWT (HS256) contém sub, name e email e expira em JWT_EXPIRES_IN (padrão 1 dia).

GET /comunicacoes

ParâmetroRegra
numeroProcessoNúmero CNJ com ou sem máscara; normalizado para 20 dígitos; inválido → 400
tribunalSigla, sem diferenciar maiúsculas
dataInicio, dataFimYYYY-MM-DD, inclusivos; data inexistente ou início > fim → 400
page, pageSizePadrão 1 e 10; pageSize máximo 50 (acima → 400)

Ordem availability_date DESC, id DESC: o id desempata comunicações do mesmo dia e mantém a paginação estável. Parâmetro vazio equivale a ausente; parâmetro desconhecido → 400.

→ 200 {

    "id": 101, "lawsuitNumber": "1234567-89.2024.8.26.0100", "lawsuitClass": "Procedimento comum",
    "court": "TJSP", "availabilityDate": "2025-08-15", "type": "Intimação",
    "documentType": null, "courtUnit": "1ª Vara Cível", "content": "…", "link": null,
    "recipients": [{ "name": "Amélia Macedo", "side": "A" }]
  }],
  "meta": { "page": 1, "pageSize": 10, "total": 1, "totalPages": 1 }
}

GET /processos/:numero (bônus)

Aceita o número com ou sem máscara e a mesma paginação de /comunicacoes. Devolve o processo (classe, tribunal, destinatários sem repetição, total de comunicações e finalJudgment) e as comunicações, cada uma com mentionsFinalJudgment. finalJudgment considera todas as comunicações do processo, não apenas a página.

POST /comunicacoes/:id/resumo (bônus)

→ 200 { "highlights": ["Prazo: 15 dias"], "summary": "Fica a parte intimada para, no prazo de 15 …" }

Resumo extrativo, sem LLM: divide o texto em frases (sem quebrar em abreviações como “art.”), pontua por termos jurídicos (prazo, audiência, sentença, intimação…) e devolve as três mais relevantes na ordem original, mais destaques extraídos por expressões regulares (prazo, audiência, trânsito em julgado). Motivos: não envia dados de processos a terceiros, não depende de chave ou custo externo e é determinístico.

Formato de erro

{ "statusCode": 400, "message": "pageSize deve ser no máximo 50.", "error": "Bad Request" }

Erros de validação podem trazer message como lista de mensagens. Todas em pt-BR.

3. Estrutura do banco de dados

PostgreSQL 16, esquema gerenciado pelo Prisma (api/prisma/schema.prisma) com migrations versionadas em api/prisma/migrations/. Tabelas e colunas em snake_case; modelos do Prisma em inglês.

TabelaDescrição e decisões
usersContas de acesso. email único e sempre em minúsculas; a senha só existe como hash bcrypt. Não se relaciona com os dados processuais (todos os usuários consultam a mesma base).
courtsTribunais, identificados pela sigla (chave natural, estável e curta).
lawsuitsProcessos, identificados pelo número CNJ só com dígitos (20 caracteres); a máscara é aplicada na saída. Guarda a classe processual.
communicationsComunicações. Mantém o id de origem, o que torna o seed idempotente. availability_date é DATE (sem hora), evitando problemas de fuso nos filtros. court_acronym é repetido (desnormalizado) para filtrar por tribunal sem junção.
recipientsDestinatários de cada comunicação (nome e polo). Removidos em cascata com a comunicação.

Índices

ÍndiceAtende a
communications (availability_date DESC, id DESC)Listagem sem filtro, já na ordem da resposta, e filtro por período
communications (court_acronym, availability_date DESC)Filtro por tribunal (com ou sem período)
communications (lawsuit_number, availability_date DESC)Filtro por número e tela do processo
recipients (communication_id)Carregar os destinatários de cada comunicação
users (email) únicoLogin e unicidade do cadastro

4. Importação dos dados (seed)

api/src/database/seed/seed.ts lê dados/tribunais.json e dados/comunicacoes.json (formato inspirado na API pública de comunicações do CNJ, como lista ou { items: [...] }) e grava no banco. Roda automaticamente a cada docker compose up.

Origem (CNJ)DestinoTratamento
idcommunications.idObrigatório, inteiro positivo
numero_processo / numeroprocessocommascaralawsuits.numberCom ou sem máscara → 20 dígitos
siglaTribunalcourt_acronymMaiúsculas; tribunal ausente é criado
data_disponibilizacaoavailability_dateAceita data com hora; data inexistente é rejeitada
tipoComunicacao, tipoDocumento, nomeOrgaotype, document_type, court_unitEspaços removidos
textocontentObrigatório
nomeClasselawsuits.class_nameOpcional
destinatarios[].nome/polorecipientsDestinatário sem nome é descartado
  • Idempotente: o lote substitui as comunicações com os mesmos ids; rodar de novo não duplica.
  • Em lotes de 500, cada um numa transação.
  • Registros inválidos são pulados e contados com o motivo no log; ids repetidos ficam com a última ocorrência.
  • Conta de demonstração (demo@exemplo.com / demo12345), criada ou atualizada a cada execução; desligável com SEED_DEMO_USER=false.

Com os dados do case: 10 tribunais, 40 processos, 120 comunicações e 311 destinatários, carregados sem nenhum registro rejeitado. Campos do arquivo ignorados de propósito: meio/meiocompleto (sempre DJEN) e destinatarioadvogados (nenhuma tela usa; seriam uma tabela de advogados por OAB se o produto passar a acompanhar comunicações por OAB).

6. Configuração e execução

Requisitos

Docker com Docker Compose; Node.js 24+ e npm.

Banco + API com os dados carregados

docker compose up -d --build
# API: http://localhost:8888 · Swagger: http://localhost:8888/docs

Front

cd web
cp .env.example .env.local     # VITE_API_URL=http://localhost:8888
npm install
npm run dev                    # http://localhost:3099

API fora do Docker

docker compose up -d db
cd api
cp .env.example .env           # gere um JWT_SECRET (instrução no arquivo)
npm install
npx prisma migrate deploy
npm run seed:dev
npm run start:dev

BancoNeon (Postgres 16 serverless, conexão direta, branch production)AWS us-east-1 (Virginia)

API e banco ficam na mesma região: cada requisição faz várias consultas em sequência, e a distância entre API e banco é o que mais pesa na latência. No plano gratuito, a API "dorme" após ~15 min sem uso (primeiro acesso em ~50 s) e o banco suspende o processamento quando ocioso (religa na primeira consulta). Migrations foram validadas antes num branch temporário do Neon; a cada deploy, o container aplica migrations pendentes e roda o seed idempotente.

Keep-alive: um pinger externo (cron-job.org) chama GET /live a cada 10 minutos das 07:00 às 23:59 (horário de Brasília), mantendo a API acordada durante o dia sem consultar o banco — o Neon continua suspendendo quando ocioso. Um agendamento no GitHub Actions (.github/workflows/keep-alive.yml) faz o mesmo como reserva; sozinho ele não bastou, porque o agendador do GitHub é "melhor esforço" e chegou a ficar mais de 1 h sem rodar. Se a API demorar mais de 5 s, o front avisa que o servidor está ligando.

8. Segurança

  • Todas as rotas exigem JWT por padrão (guard global); as públicas são marcadas explicitamente.
  • Senhas com bcrypt; limite de 72 caracteres para não aceitar senha truncada.
  • Login sem enumeração de usuários (mesma mensagem e tempo semelhante para e-mail inexistente).
  • Entrada validada com lista branca de campos (campo desconhecido → 400).
  • Segredos só por variável de ambiente; validação na subida.
  • Container da API roda como usuário sem privilégios.
  • O resumo não envia dados de processos a serviços externos.
  • Front: token em localStorage (trade-off documentado: o contrato devolve o token no corpo do login); sessão encerrada automaticamente em qualquer 401.
